# DEFENSE GUIDE — Web Inventory Management System

> Цель этого документа: дать тебе готовую систему объяснений проекта так, чтобы ты говорил уверенно, логично и технически корректно на защите и на собеседовании.
>
> Важно: это не «зазубрить текст», а карта, по которой ты понимаешь **почему** каждая часть сделана именно так.

---

## 0) Короткий контекст проекта

Проект — веб-система управления инвентарями (оборудование, книги, документы и т.п.), где:

- есть **инвентари** (шаблоны/контейнеры),
- есть **элементы (items)** внутри инвентарей,
- есть **кастомные поля** (до 3 каждого типа),
- есть **кастомные ID** (настраиваемый формат),
- есть **права доступа** и публичность,
- есть **обсуждения (discussion)** в near real-time,
- есть **поиск**, **лайки**, **админ-панель**.

Стек:

- Frontend: React + Ant Design + React Router + i18next + socket.io-client
- Backend: Node.js + Express + Sequelize
- DB: PostgreSQL
- Realtime: Socket.IO

## 2) Архитектура проекта (понятно и без воды)

### 2.1 Слои

1. **UI слой (React components/pages)**
   - отвечает за отображение, формы, UX, табы, таблицы.
2. **API слой на клиенте**
   - единая точка HTTP-запросов: `client/src/services/api.js`.
3. **Backend routes + business logic**
   - валидация, права доступа, генерация ID, optimistic locking.
4. **Persistence (PostgreSQL + Sequelize models)**
   - целостность, индексы, связи, ограничения.
5. **Realtime transport (Socket.IO)**
   - комнаты по inventory и push новых комментариев.

### 2.2 Почему это хорошо для защиты

- Слои разделены — легко объяснить, где какая ответственность.
- Изменения в UI не ломают бизнес-логику и наоборот.
- Безопасность не завязана на фронт: права и проверки дублируются на сервере.

## 3) Модель данных (самая важная часть для комиссии)

### 3.1 Основные сущности

- `User`
- `Inventory`
- `InventoryField`
- `Item`
- `InventoryAccess`
- `Discussion`
- `ItemLike`
- `Tag`
- `Category`

### 3.2 Почему кастомные поля **не** в JSON

Аргументация (обязательно проговори):

- По ТЗ: максимум 3 поля каждого типа.
- Значит выгодно и корректно хранить значения в фиксированных колонках (`textField1..3`, `numberField1..3`, ...).
- Метаданные (название, описание, порядок, showInTable) — отдельно в `InventoryField`.
- Это даёт:
  - простые агрегации по SQL,
  - предсказуемую схему,
  - меньше сложности при редактировании набора полей,
  - нормальную производительность без document-хаоса.

### 3.3 Custom ID и уникальность

- В `Item` есть глобальный PK (`UUID`) и отдельный `customId`.
- `customId` **не** PK, потому что должен быть уникален только в рамках inventory.
- Уникальность обеспечивается индексом `(inventoryId, customId)`.
- Это прямое выполнение ТЗ.

### 3.4 Версионирование (optimistic locking)

- `Inventory.version` инкрементируется при каждом изменении.
- Клиент отправляет текущую версию.
- Если версия устарела — сервер возвращает `409 Version conflict`.
- Аналогично заложен `version` и для `Item`.

## 4) Backend: что именно реализовано и где

### 4.1 Главные файлы

- `server/src/app.js`
  - инициализация Express,
  - middleware (CORS, session, passport),
  - подключение маршрутов,
  - запуск Socket.IO,
  - DB sync.

- `server/src/routes/inventories.js`
  - CRUD inventory,
  - items CRUD,
  - fields CRUD,
  - access list,
  - discussions,
  - likes,
  - search,
  - tag cloud,
  - suggest users.

- `server/src/routes/admin.js`
  - управление пользователями для admin.

### 4.2 Realtime Discussion

В `app.js`:

- `joinInventory` → `socket.join('inventory:<id>')`
- `leaveInventory` → `socket.leave(...)`
- `sendComment`:
  1. сохраняет комментарий в БД,
  2. отправляет `newComment` всем в комнате.

Почему room-подход правильный:

- изоляция событий по конкретному inventory,
- меньше лишнего трафика,
- масштабируемо по логике.

### 4.3 Search

Используется Postgres full-text (`to_tsvector/plainto_tsquery`) + fallback `ILIKE`.

Почему так:

- full-text лучше для релевантности,
- fallback защищает от edge-cases,
- решение практичное для MVP/учебного проекта.

## 5) Frontend: как объяснить структуру

### 5.1 Важные файлы

- `client/src/services/api.js` — единая точка запросов и ошибок.
- `client/src/pages/InventoryDetail.jsx` — главный экран inventory с табами.
- `client/src/components/Inventory/*` — вкладки Settings/Custom IDs/Access/Fields/Stats.
- `client/src/components/Discussion/DiscussionTab.jsx` — комментарии с Socket.IO.
- `client/src/pages/Home.jsx` — latest/top/tag cloud/search mode.
- `client/src/pages/Admin.jsx` — admin table + toolbar массовых действий.

### 5.2 Почему InventoryDetail — центр домена

`InventoryDetail` агрегирует:

- загрузку inventory + userAccess,
- загрузку items + fields,
- управление модалкой item,
- автосохранение настроек,
- динамическую доступность вкладок по ролям.

Это удобная композиция для одной «предметной страницы».

### 5.3 Автосейв

В settings:

- изменения помечают draft как dirty,
- таймер раз в 8 секунд пытается сохранить,
- при конфликте версий страница перезагружает данные.

Это соответствует требованию «не сохранять на каждый символ».

## 7) Custom ID — как объяснить глубоко

### 7.1 Концепция

Custom ID — это формат из элементов:

- text,
- random (6/9 digits, 20-bit, 32-bit),
- guid,
- datetime,
- seq.

### 7.2 Где хранится

`Inventory.customIdFormat` хранится как JSON-строка массива элементов.

Пример:

```json
[
  { "type": "text", "value": "INV-" },
  { "type": "datetime" },
  { "type": "text", "value": "-" },
  { "type": "seq", "width": 4 }
]
```

### 7.3 Как генерируется

При создании item:

1. сервер читает `customIdFormat`,
2. проходит по элементам,
3. собирает строку,
4. вставляет в `Item.customId`,
5. БД валидирует уникальность через индекс.

### 7.4 Почему генерация на сервере

- нельзя доверять клиенту для уникальности,
- единая логика независимо от UI,
- проще контролировать коллизии.

## 8) Fields DnD — как объяснить

### 8.1 Что делает вкладка Fields

- создаёт поле,
- удаляет поле,
- включает/выключает `showInTable`,
- меняет `order` через drag-and-drop.

### 8.2 Как устроен reorder

1. Пользователь перетаскивает карточки.
2. На клиенте временно пересчитываются order.
3. Пакетом отправляются update-запросы на сервер.
4. При ошибке — откат reload().

### 8.3 Почему dnd-kit

- совместим с React 19,
- современный и поддерживаемый,
- гибкая интеграция без heavy legacy.

## 11) Вопросы комиссии (hard mode) и как отвечать

### 1) Почему не сделали динамические таблицы под каждый inventory?

Ответ:

- Это избыточно и рискованно для миграций.
- ТЗ ограничивает поля до 3 каждого типа.
- Фиксированная схема быстрее, проще, безопаснее в поддержке.

### 2) Где предотвращается duplicate custom ID?

Ответ:

- На уровне БД: unique index `(inventoryId, customId)`.
- Это сильнее, чем любые проверки на фронте/бэке.

### 3) Почему optimistic locking, а не pessimistic?

Ответ:

- Меньше блокировок, лучше UX для веба.
- Конфликты редки, но корректно обрабатываются через 409.
- Для коллаборативного редактирования это практичный стандарт.

### 4) Как избежать N+1 запросов?

Ответ:

- Использую include/join в Sequelize.
- Счётчики/агрегации считаю пакетно (`COUNT`, группировки).
- Не запускаю запросы в цикле без необходимости.

### 5) Как обеспечить безопасность API?

Ответ:

- `requireAuth`/`requireAdmin` middleware,
- серверная проверка прав на каждом mutation endpoint,
- сессии и cookie-флаги,
- CORS с credential policy.

### 6) Что будет, если сокет упал?

Ответ:

- Socket.IO сам делает reconnect.
- Для отправки комментария предусмотрен HTTP fallback.

### 7) Почему API-слой на клиенте отдельно?

Ответ:

- единая обработка ошибок,
- меньше дублирования fetch,
- проще тестировать и рефакторить.

### 8) Почему лайк toggle, а не два endpoint’а like/unlike?

Ответ:

- Для UI проще один action.
- На сервере проверяю существование, затем create/delete.
- Состояние возвращается в одном формате (`count`, `likedByMe`).

### 9) Где реализована масштабируемость?

Ответ:

- Search через PostgreSQL FTS, можно добавить GIN index.
- Room-модель realtime масштабируется через adapter (например Redis) при росте.
- Разделение слоёв упрощает горизонтальное развитие.

### 10) Почему именно Sequelize?

Ответ:

- Быстрый старт для учебного проекта,
- удобно выражать связи,
- баланс между SQL-контролем и скоростью разработки.

## 12) Техсобес: вопросы по JS/React/Node конкретно под твой проект

### React

1. Почему `useCallback` в `InventoryDetail`?
- Чтобы стабилизировать ссылки функций для `useEffect` и избежать лишних перезапусков.

2. Зачем `useMemo` для колонок таблицы?
- Чтобы не пересоздавать конфиг колонок на каждый рендер.

3. Почему нельзя делать impure операции в render?
- Нарушается детерминированность рендера, React предупреждает и может вести к багам.

4. Что такое controlled form и где ты это используешь?
- В AntD формах через `Form` и `onFinish/onValuesChange`.

### Node/Express

1. Зачем middleware-цепочка?
- Разделяет cross-cutting concerns (auth, parsing, sessions, CORS).

2. Почему проверка прав в каждом endpoint, а не только на роут-группе?
- Потому что разные endpoints могут требовать разные уровни доступа.

3. Как ты обрабатываешь ошибки?
- try/catch в роуте + осмысленный HTTP статус + сообщение.

### SQL/DB

1. Как объяснишь составной индекс?
- Индекс по двум колонкам, обеспечивает уникальность пары, а не каждой отдельно.

2. Чем `COUNT + GROUP BY` лучше подсчёта в JS?
- DB оптимизирована для агрегаций, меньше трафика и памяти на сервере.

Как отвечать:

1. Добавлю новый descriptor в фронт-палитру.
2. Добавлю обработку этого `type` в серверном генераторе.
3. Покрою preview на клиенте.
4. Проверю коллизии/валидность.

### Сценарий B: «Сделай сортировку access по email»

- Уже поддержано, переключается режим sort в Access tab.

### Сценарий C: «Покажи, где enforced лимит до 3 полей типа»

- В backend `POST /fields` делается `count` по `fieldType` и ограничение.
- Плюс уникальность `(inventoryId, fieldType, fieldIndex)`.

## 14) Частые ошибки на защите (и как не попасть)

1. **Говорить только про UI**
   - Комиссия хочет слышать БД, доступы, индексы, конкуренцию.

2. **Путать “есть кнопка” и “есть безопасность”**
   - Всегда подчёркивай: серверная валидация — обязательна.

3. **Обещать 100% без оговорок**
   - Честно говори: что завершено, что MVP, что следующая итерация.

4. **Не уметь пройти по одному запросу end-to-end**
   - Тренируйся: клик → frontend handler → API → backend route → model/DB → response.
